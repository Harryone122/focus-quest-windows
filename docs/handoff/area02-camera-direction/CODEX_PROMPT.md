# 給 Codex 的 prompt：苔痕驛站故事事件運鏡

（整段貼給 Codex。全部用繁體中文回覆。）

---

你是 Focus Quest（Windows Electron + React + SQLite + three.js r128）的正式前後端實作者。設計由 Claude 負責，你負責實作、測試與整合。這個任務是實作 **苔痕驛站（Area 02）故事事件的運鏡**。

## 背景

使用者實際玩過後回報：首訪（提燈漂走）和二訪（住宿簿的畫）發生時，鏡頭一直停在整張地圖的遠景，旅人只在角落做很小的動作，看起來像遊戲卡住了。Claude 已經在原型裡設計並驗證了每個事件的運鏡，也找出幾個「畫面上根本看不到」的原因（旅人被自己擋住住宿簿、提燈被大樹擋住、燈柱刻字太小又背對鏡頭）。你要把這些做進正式遊戲。

## 先讀（都在 `docs/handoff/area02-camera-direction/`）

1. `camera-direction.md`：設計說明、每個事件的鏡頭表、通用規則、要同步的場景物件修改、未解決的問題。
2. `camera-keys.json`：10 個故事事件的關鍵影格資料（`p`、`at`、`z`、`el`、`az`）。
3. `prototype-camera.diff`：原型（`prototypes/moss-station.html` 的 partC／partD）這次的差異，是行為的參考實作：`DIR`、`dirShot()`、`stepDirector()`、`lanternAt()`、`placeCamera()` 與場景物件修改。
4. `moss-station.html`：可以直接打開的測試頁；按「試看新事件」逐一播放，右邊的「運鏡：開／關」可以比較有無運鏡。
5. `previews/`：每個事件的目標畫面（標了事件進度 p）。

另外參考既有的 `docs/AREA_02_MOSS_STATION_EVENTS.md` §19、`docs/area-02-moss-station.scene.json` 的 `storyEvents`、以及你已經實作的 `src/renderer/src/mossStation/mossStationScene.js`／`MossStationFocusScene.tsx`。

## 工作流程（使用者要求，不能省略）

1. **先不要實作。** 目標畫面已經由 Claude 做好（`previews/`）。請先用你自己的話確認你理解每個事件的鏡位，並指出你認為正式場景裡會和原型不同的地方（例如玻璃上下緣、aspect、現有的 focus 取景），列出來等使用者確認方向。
2. 使用者確認後才實作。
3. 實作完成後，**先給使用者一個他自己能試的測試網頁／測試入口**（可以逐一播放這 10 個事件、有「運鏡開關」、可以拖進度條到任意 p），讓使用者自己看過、和 Claude 討論修正後再收尾。不要只貼截圖就說完成。

## 要做的事

### A. 運鏡（核心）

1. 在共用的聚焦場景層加一個「導演鏡頭」：輸入是事件 id 與進度 p，輸出是鏡頭狀態（中心、zoom、額外仰角 el、額外方位角 az）。
   - 資料用 `camera-keys.json` 的格式；把它併入 `docs/area-02-moss-station.scene.json` 每個 `storyEvents[]` 的 `camera.keys`（先確認檔案沒有被別人改過再寫，保留現有格式）。
   - `at` 的四種寫法：`[u,v,y]` 地圖座標（用場景既有的 `W(u,v,y)`）、`"traveller"`（旅人位置上方 0.7）、`"lantern"`（漂流提燈**目前的位置**，必須用畫提燈的同一個函式／曲線算，不要另存）、`"home"`（原本整張地圖的中心）。
   - 兩個關鍵影格之間用 smoothstep `x²(3−2x)`；`z` 用對數內插，`at`/`el`/`az` 線性。第一格之前、最後一格之後維持不變，最後一格一律是 `home, z=1`。
2. 鏡頭狀態是**事件進度 p 的純函數**。p 必須和 `storyUpdate(p)` 用的是同一個（來自後端保存的事件動作與 `sceneNow`，不是前端自己另計時）。暫停時 `sceneNow` 凍結，鏡頭跟著停。
3. 平滑：目標狀態經過一個臨界阻尼彈簧（時間常數 0.55 秒），讓進場、退場與突然跳動都順。**場景剛建立、重新開啟視窗、從背景回來、或進度被快轉時，鏡頭直接跳到當時進度該有的鏡位（snap），不要從 home 慢慢移過去。**
4. 實作用 `camera.zoom`（z=1 等於現有取景）。檢查所有依螢幕像素的東西在 z 到 10 時仍正確：水面著色器的 `pxPerUnit`（要除以 zoom）、雨絲、霧／粒子的大小、陰影。
5. 取景規則：
   - 現有的上下玻璃（header/footer）與 `chrome insets`、`edgeGlass`：z>1 時，主體要放在上下玻璃之間的可視帶中央；`edgeGlass` 的場景取樣要跟著鏡頭更新（注意不要一直重新取樣造成閃爍，節流即可）。
   - 開場事件照現有規則 `reportCinematic(true)` 隱藏介面；其他事件保留玻璃。
   - 16:9、16:10、4:3、21:9 與窄視窗：畫面邊緣不能出現空白、地圖邊或背景接縫。
   - 太陽目標點固定在 home，不跟著鏡位移動；z≥5 時檢查陰影沒有明顯鋸齒或跳動，必要時只針對近景調整陰影範圍。
6. 拖曳偷看（yaw/pitch 偏移）要繼續能用：疊加在運鏡上，放開後照原本速度回彈到運鏡位置。
7. 「減少動態」（系統偏好或遊戲設定）：不做連續推拉與跟拍，改成在鏡位之間 0.4 秒淡入切換；跟拍提燈改用該段最接近的固定鏡位。請把你的做法在確認階段告訴使用者。
8. 只對「故事事件」啟用，一般事件維持原本的 home 取景。機制要放在共用層，之後別的地圖的故事事件可以用同一份資料。
9. **不得改變**：燈的點亮規則、天氣、排程、線索、保存、後端資料；故事事件仍然只是播放已保存的狀態。

### B. 為了讓鏡頭看得到東西，場景物件要同步修改（見 `camera-direction.md` §5 與 `prototype-camera.diff`）

1. 燈柱刻字改成釘在柱上、朝向遊戲鏡頭的刻字牌（0.2×0.52×0.03，字面 0.17×0.46；青苔墊 1.15×2.7×0.45）。
2. 漂流提燈放大 1.7 倍；雨天水痕圈 1.5 倍、不透明度 0.55。
3. 首訪（晴）與舊燈芯事件最後（p 0.76–0.95），霧谷浮出 7 點淡淡的遠方燈光（加色混合、輕輕上下飄、之後淡出）。

### C. 先只做預覽、等使用者同意才實作：穿透剪影

柴堆（`l_wood`）的旅人從任何角度都被大樹根蓋住，運鏡救不了。建議做一個**全遊戲通用**的「旅人被場景擋住時，疊一層半透明輪廓」（例如用 `depthFunc: GreaterDepth` 再畫一次旅人，平塗、低不透明度，顏色跟著時間與天氣）。這會影響所有地圖，所以請**先出靜態預覽圖**（柴堆、售票窗口、一個雨天畫面），讓使用者確認風格再做；不要直接合進去。

## 驗收標準

1. 十個事件逐一播放，每個鏡位都和 `previews/` 的目標畫面一致（構圖、主體可見、側轉方向正確）；差異請解釋。
2. 首訪（晴／雨）：玩家能一直看到提燈，從出現到落進霧瀑，旅人站起來目送時旅人與瀑布同時入鏡。
3. 二訪：玩家看得到住宿簿被翻開、畫滑出來、角落的字。
4. 任何事件中，不會有超過 8 秒完全沒有動作或鏡頭變化的整張遠景。
5. 事件結束時鏡頭回到 home，且和事件開始前的取景相同（沒有累積偏差）。
6. 暫停、繼續、中途重開視窗、快轉到事件中段：鏡頭立刻是對的。
7. 拖曳偷看仍然可用；減少動態可用。
8. 四種 aspect 與上下玻璃都沒有問題；沒有陰影或水面異常；沒有掉幀（在 Windows Electron 實機看）。
9. 自動測試：`dirShot(eventId, p)` 的純函數測試（所有 `at` 都能解析、鏡頭在 p 上連續、z 在 1–12、最後一格是 home）；現有的 vitest（含 moss 的 12 個測試）與 typecheck 全過。
10. 不要動使用者的存檔；QA 用獨立資料夾。

## 工作規則

- 同一時間只有一個 agent 寫 repo；開始前先看 `git --no-optional-locks status` 和相關檔案的修改時間，如果別人（Claude 或另一個 Codex）正在改同一批檔案，先停下來告訴使用者。
- 不要用 reset / clean / stash / push，不要整個資料夾覆寫。
- `App.tsx`、`LobbyScene.tsx`、企畫書與 brief 是 CRLF，保持不變。
- 先說你要做什麼，做完只回報：結果、檔案、沒做到的地方、需要使用者決定的事。不要複述過程。
